# ADR-021 — `color` como `ColorExtended` (modo escala + plano) y prop `gradient` en componentes

- **Estado**: aceptada · 2026-07-20 (checkpoint con el propietario)
- **Contexto**: el contrato ya define `ColorExtended` (roles semánticos + 16 paletas + shades + alpha + `white`/`black`/`inherit`/`currentColor`/`transparent`/`#hex`) y lo usan `ColorsProps.c/bg` y `BorderProps.bdc`. Además `VariantProps.gradient = { from: ColorExtended; to: ColorExtended; deg?; animate? }` ya está en el contrato. Pero `Button.color` quedó como `SemanticScaleName` (solo 7 roles) e ignoraba `gradient`, inconsistente con el resto de props de color. El obstáculo: `color` en Button **no es "pinta este color"** sino **"usa esta ESCALA de 11 pasos"** — las recetas de variante resuelven `scale.600` (filled), `scale.700` (hover), `scale.500.12` (light), etc. Un color suelto no tiene 11 pasos, y el contrato CSS solo expone las 7 escalas de rol (no las 16 paletas crudas).
- **Decisión**: cualquier prop de color de componente usa **`ColorExtended`** (convención). `Button.color: ColorExtended` con **dos modos de resolución** en `ResolveVariant`:
  - **Modo escala** — cuando `color` es uno de los 7 nombres de escala semántica (`primary|accent|gray|success|warning|error|info`): comportamiento actual. La receta resuelve contra la escala de rol del tema (CSS vars); **theme-adaptive**.
  - **Modo plano** — cualquier otro `ColorExtended` (nombre/shade de paleta, `#hex`, `white`/`black`, role token): el color es un **base único** y las variantes se derivan de él: `filled` bg=base (hover/active vía `color-mix` oscureciendo), `light` bg=base con alpha + fg=base, `outline`/`ghost` fg/borde=base con hover alpha, `glow` bg=base. El foreground legible de `filled` se calcula por **luminancia** cuando el base es un color concreto (hex, o hex de paleta desde `@stellaria/nebula-tokens`); para bases que son CSS var (shade semántico/role token) cae a blanco. Las paletas crudas se resuelven a su **hex** de tokens (theme-independent): el modo plano es un **escape hatch** que NO se adapta entre temas — es la contrapartida asumida de permitir color arbitrario.
  - **`gradient` prop** (`{ from: ColorExtended; to: ColorExtended; deg?; animate? }`): cuando `variant="gradient"` y el prop está presente, sobrescribe el fondo con `linear-gradient(deg, from, to)` (from/to resueltos como `ColorExtended`; `deg` default 135). Sin prop, `gradient` usa `theme.effects.gradients.brand` (como hasta ahora). `animate: true` anima la posición del gradiente.
- **Alternativas**:
  - `color: ColorScaleName` (7 roles + 16 paletas) metiendo las paletas al contrato CSS: rechazada — infla el CSS por tema (+176 vars) y expone paletas crudas como escalas de componente, diluyendo el principio de "solo roles" sin dar el hex/keyword que el propietario quiere.
  - Mantener `color: SemanticScaleName` y solo añadir `gradient`: rechazada — el propietario quiere `ColorExtended` como convención de props de color.
- **Consecuencias**:
  - `packages/web` gana lógica de resolución de `ColorExtended` + modo plano en `resolve-variant.ts` (importa `palettes` de tokens para los hex de paleta) y un `import`/utilidad de luminancia.
  - El modo plano con colores concretos **no es theme-adaptive** (documentado como escape hatch). El modo escala y el default siguen siendo theme-safe.
  - API pública de Button ampliada (`color` más ancho, nuevo `gradient`). Actualiza `Button.md` y la anatomía de ADR-018 si aplica. Los ~200 componentes siguientes que expongan color usan `ColorExtended` (convención).
  - Contraste: modo escala y default siguen validados por `check:contrast`; el modo plano con hex arbitrario queda fuera del gate (responsabilidad del consumidor del escape hatch).
